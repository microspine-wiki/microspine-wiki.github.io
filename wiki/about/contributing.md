# Contributing

The wiki gets better when people who build spine mechanisms write down what they know. You do not have to write a whole page to help.

## Ways to help

- **Report an error.** A wrong number, a misread paper, a broken link. Open an issue, say where it is, and if you can, cite the source that gives the right answer.
- **Add data.** Measurements on a surface not yet covered, a test of a toe design, a photograph of a failure. Small results are very useful if they are well described ([Open questions](../reference/open-questions.md)).
- **Add a source.** A paper, thesis or report that a page should cite.
- **Write or extend a page.** Pages marked *stub* or *draft* need the most work.
- **Review a page.** Check every number and claim against its sources and report what you find. A page becomes *reviewed* only after someone other than its author has done this.

Changes go through the project's Git repository: edit a file on GitHub or in a clone, then open a pull request. Every page lives under `wiki/` at the same path as its address on the site, so a quick correction can be made directly in GitHub's editor.

## Ground rules

1. **Cite what others can read.** Every factual statement needs a source that someone else can check: a published paper, a thesis, a report in a public repository, a data sheet, or measurements described well enough to repeat. Cite the original work, not a review or another page of this wiki.
2. **Use your own words.** Summarise and explain. Quote only short passages, and mark them as quotations. Do not paste text or figures from papers.
3. **Mark your own analysis.** A derivation, estimate or rule of thumb that is not in a source is welcome, but say that it is the wiki's own, as [Sizing spine pads for a limbed climber](../climbing/sizing-a-limbed-climber.md) does.
4. **Publish only what you may.** No unreleased reports, review slides, internal documents, data or photographs without the permission of whoever holds the rights, however you came by them. See [Material that is not cleared](#material-that-is-not-cleared).
5. **Give numbers with units and conditions.** Say what surface, how many spines, what speed, and whether the figure is a mean, a best case or a single trial.
6. **Be fair to the people whose work you describe.** Report results as their authors did. Where you disagree, say why and cite your evidence.

## Style

- **English with British spelling**, as in the rest of the wiki: "centre", "programme", "behaviour".
- **SI units.** Where a source used other units, give them too: 145 lb (66 kg).
- **Short sentences and plain words.** Readers include students and engineers from other fields. Define a term the first time a page uses it, or link to the [glossary](../reference/notation-and-glossary.md).
- **The wiki's notation**: forces are those of the wall on the spine, normal force is negative in adhesion, and angles are measured from the wall ([Notation and glossary](../reference/notation-and-glossary.md#axes-and-signs)).
- **Headings in sentence case**, with no math in them: anchors would differ between this site and GitHub.

## Working on the files

The wiki is plain Markdown, which reads correctly on GitHub and in Obsidian, plus a small generator that turns it into this website.

| Path | What it holds |
|---|---|
| `wiki/` | the pages, one Markdown file each, in the same folders as on the site |
| `wiki/SUMMARY.md` | the page list in the sidebar, in reading order |
| `wiki/assets/figures/` | original figures as SVG, generated by the scripts in `figures/` |
| `wiki/assets/thesis/` | figures reproduced from another work, listed in [Credits and licences](credits.md) |
| `wiki/assets/archive/`, `wiki/assets/video/` | photographs and videos from the laboratory's project wikis, also listed there |
| `data/references.json` | the bibliography |
| `figures/` | the scripts that draw the original figures |
| `tools/` | Python scripts: the stalk model, the climber load analysis, the bibliography generator and the figure extractor |
| `theme/` | the site's stylesheet, script and interactive tools |
| `build.mjs`, `lib/` | the site generator |

To preview the site you need [Node.js](https://nodejs.org/) 20 or later, and nothing else:

```sh
node build.mjs           # build into _site/ and list any problems
node build.mjs --serve   # preview at http://localhost:4173, rebuilt on every change
```

The build stops with an error on a broken link or anchor, an image that is missing or has no alt text, math that does not parse, or third-party media that is not in the credits. Fix every error before you open a pull request. Warnings, such as a file no page uses, are worth a look too.

## Writing a page

A page is a Markdown file with a short header:

```markdown
---
description: One or two sentences on what the page answers. Shown under the title and in search results.
status: draft
---

# Title of the page

Opening paragraph.

## First section
```

- **One `#` title per page.** Sections start at `##`.
- **`status`** is `stub`, `draft` or `reviewed` ([what they mean](about.md#how-far-to-trust-it)).
- **Add the page to `wiki/SUMMARY.md`** under its group, or it will have no entry in the sidebar.
- **Link to other pages by their file**, with a relative path, such as `[Load sharing](../design/load-sharing.md#loading-lines)`. The build checks every internal link and anchor. An anchor is the heading in lower case, with punctuation dropped and spaces replaced by hyphens, as on GitHub.

Beyond plain Markdown:

| To get | Write |
|---|---|
| a citation | `[Asbeck 2010][asbeck2010]`, with `[asbeck2010]: ../reference/bibliography.md#asbeck2010` at the foot of the page |
| inline math | `$T = W h / L$` |
| displayed math | a line with only `$$`, the expression, then another line with only `$$` |
| a figure with a caption | the image on its own line, then a paragraph in italics directly below it |
| a callout | a quotation whose first line is `> [!NOTE]`, or `TIP`, `IMPORTANT`, `WARNING`, `CAUTION` |
| a collapsible block | `<details>` and `<summary>` around it, with blank lines inside |
| a video | `![What happens in it](../assets/video/name.mp4)`, with an italic caption below; a still named `name.poster.jpg` beside it becomes the poster |
| an interactive tool | `<!-- widget: name -->` on a line of its own |

## Adding a reference

References live in `data/references.json`, and the [bibliography](../reference/bibliography.md) is generated from that file.

1. Add an entry. The easiest way is to copy an existing entry of the same type and replace every field:

   ```json
   {
     "key": "smith2027",
     "authors": ["Smith, Jane Q.", "Lee, Min"],
     "year": 2027,
     "title": "Title exactly as published",
     "venue": "Journal or conference",
     "volume": "12",
     "issue": "3",
     "pages": "101-112",
     "doi": "10.0000/example",
     "url": "https://doi.org/10.0000/example",
     "oa_url": "https://example.org/an-open-copy.pdf",
     "type": "journal",
     "category": "grippers",
     "summary": "Two or three sentences on what the work contributes, from its abstract.",
     "verification": "Where the details were checked, for example its Crossref record."
   }
   ```

2. Check the details against the publisher's page or the work's Crossref record, not against another paper's reference list, which often contains mistakes.
3. Regenerate the page with `python3 tools/make_bibliography.py`.
4. Cite the work by the label the bibliography shows, here `[Smith & Lee 2027][smith2027]`, and put the link definition at the foot of the page.

The key is the anchor that pages link to, so never change the key of an entry that is already cited. `category` is one of the groups listed at the top of `tools/make_bibliography.py`. Web pages, patents and data sheets use `"category": "web"` and give a `label` and a `citation` in place of the bibliographic fields. If two works would get the same label, give both an explicit `label` such as "Quaine 1997a" and "Quaine 1997b"; the script refuses to run until you do.

## Adding a figure

**Original diagrams and charts** are SVG files, each drawn by a short script in `figures/` with the helpers in `figures/lib.mjs`. To change one, edit its script, run `node figures/build.mjs name`, and commit the script and the SVG together. The conventions are in `figures/README.md`: a white plate 720 units wide, the four checked series colours in a fixed order, text in the two ink colours, and labels on the lines rather than in a distant legend. Hand-drawn SVGs are welcome too, if they follow the same conventions and contain no scripts or links to other files.

**Your own photographs and plots** are welcome. List each file in [Credits and licences](credits.md) with your name or handle and its licence, CC BY 4.0 unless you choose otherwise. The build checks that every photograph or other raster image on the site is listed there.

**Videos** go in `wiki/assets/video/` as MP4 files (H.264, no wider than 640 pixels), each with a poster still. Keep them as short as will show the point, and under about 15 MB each: every byte is downloaded by everyone who clones the repository. List them in [Credits and licences](credits.md) as you would a photograph.

**Every image needs alt text** that says what the picture shows, and a caption, in italics, directly below it. The alt text serves readers who cannot see the picture; the caption serves everyone.

**Figures from other works** may be used only if their licence allows it, and only unaltered if the licence forbids adaptations, as the Creative Commons "ND" licences do. Put the file in a folder named after its source, give the source and licence in the caption, and add the file to [Credits and licences](credits.md). Never link to an image on another site: the build rejects it. When in doubt, draw a new figure from the published numbers and cite them.

## Interactive tools

A tool is a script in `theme/widgets/` that registers itself under a name and draws into the box a page reserves with `<!-- widget: name -->`. Follow the pattern of `theme/widgets/stalk-model.js`. Keep tools free of dependencies, usable with the keyboard, and consistent with the page's text and with the matching script in `tools/`. A page must still make sense without its tool, because GitHub and Obsidian do not run it.

## Material that is not cleared

You may have notes, photographs or data that you expect to publish but cannot yet, because you are waiting for a co-author, a sponsor or a university. Keep them in `pending/wiki/`, a folder that mirrors `wiki/` and that Git ignores.

- A page in `pending/wiki/` appears in your local preview with a banner marking it as a local draft. It is never published.
- To give it a sidebar entry, add `nav: Group name` to its front matter.
- A file in `pending/wiki/` with the same path as a public page replaces that page in your preview, so you can draft changes to it in private.
- `node build.mjs --public` builds exactly what will be published, without `pending/`. The published site is always built this way.

When the material is cleared, move it into `wiki/`, cite it, and record the permission in the pull request. Never commit `pending/`, and never paste its contents into an issue or a pull request.

## Reviewing a page

1. Read the page against every source it cites. Check each number, each attribution, and each statement that something was shown or found.
2. Redo the arithmetic in worked examples, and run the matching script in `tools/` if there is one.
3. Note anything that has no source, and any source that does not say what the page says.
4. Open a pull request with your corrections. When nothing is left to correct, change the page's status to `reviewed` and say in the pull request what you checked.
